DWG 01

General notes

From electrician to backend engineer.

I started my career in construction and electrical work. I was coordinating with teams, reading plans, and wiring systems that had to be safe, reliable, and maintainable. I completed my apprenticeship, earned my journeyman card, and led crews on commercial jobsites. That work taught me craftsmanship, patience, and how to stay calm under pressure.

Over time I got hooked on the logic behind automation and control systems. Eventually that pulled me into software. Now I use the same mindset to design APIs, databases, and services that solve problems for people instead of just chasing hype.

Note 01 · How I learn new domains

I pick up new domains fast. Podcasting pulled me in, and I taught myself how a platform actually works (RSS distribution, hosting economics, the AT Protocol as an identity and record layer) well enough to architect one. That's the pattern: get curious, learn the domain honestly, then build.

I care about honesty, ownership, and better systems. That shows up in the tools I use (Python, FastAPI, Postgres, ATProto), the projects I build, and the way I learn: in public, without pretending to have it all figured out.

Brand pillars

  • Craftsmanship: do it right, not just fast.
  • Purpose: build things that make life better.
  • Calm clarity: break problems into clear steps.
  • Independence: prefer open, user-owned systems.

Outside of code

I live in Pacifica, CA (SF Bay Area) with my wife and our dogs. Outside of work you'll usually find me gaming, hiking and exploring areas I haven't been, and going down rabbit holes of topics that are interesting and new to me.

A-01

VoxPort: creator tools on the AT Protocol

Fastify · Next.js · ATProto

Decentralized creator tools where podcasters own their identity, feed, and audience. Built on the AT Protocol with custom lexicons and a Fastify/Next.js stack to keep creator data portable and under their control. Also published an AT Protocol skill on skills.sh to help others build on the protocol.

  • 1 Federated ingestion at scale: resilient WebSocket consumer with bounded memory backpressure (1,000-event cap) and 100-event batching. Together with in-memory caching and longer cursor flush intervals, this cut production DB operations 96%, from ~209K to ~3K to 8K per day.
  • 2 Audio extraction worker: dedicated ffmpeg worker with SSRF guards, FOR UPDATE SKIP LOCKED job claiming, and Cloudflare R2 content-addressed storage.
  • 3 Multi-env production deploy: API on Fly.io, web on Vercel, Postgres on Prisma Postgres, with Sentry + Axiom + OpenTelemetry observability.

NOTE:I care about ownership and systems that don't trap people. This project pushes me to think beyond a single app and into protocols and ecosystems.

A-02

nfl-dagster: NFL contract value pipeline & ask tool

Python · Dagster · Snowflake · dbt

A production ELT pipeline and grounded LLM ask tool. Dagster orchestrates NFL play-by-play, schedules, and contract data (2015 to present) into Snowflake RAW, STAGING, and MARTS layers via dbt, then publishes finished marts to Postgres for a public website with a Claude-powered question tool that only states numbers it got from a query.

  • 1 Production ELT: 20 Dagster assets with season partitions, refreshed on schedule by Dagster+ Serverless. Each load deletes, copies, and audits inside one Snowflake transaction and rolls back on failure; 43/43 dbt tests passing in prod.
  • 2 Audited serving layer: finished marts publish to Postgres in a single-transaction swap, verified against Snowflake by row counts and primary-key fingerprints, so the website never queries the warehouse.
  • 3 Grounded LLM Q&A: a Claude Haiku tool loop over select-only, parameterized, read-only queries with timeouts and row caps. The code rejects any number not returned by a query; an 81-question eval suite scores 78/81 (30/30 refusals) at ~$0.0005 and 4s per question.

NOTE:Ran like production: rate limits, spend caps, no stored user data, required CI checks, least-privilege roles, and a monthly resource monitor.

A-04

doc-lok: pre-prompt context condenser

TypeScript · Node.js · Zero-dep

A pre-prompt middleware that condenses link-bearing Markdown by resolving remote links into compact cryptographic markers, cutting context token consumption and API latency for LLM workflows. Published on npm with zero runtime dependencies.

  • 1 Context window optimization: condenses prompt payloads by replacing unchanged remote Markdown links with compact markers, drastically cutting token usage.
  • 2 Conditional caching pipeline: two-phase network verification using HTTP HEAD probes and If-None-Match ETag validation to skip unchanged resources.
  • 3 Zero-dependency architecture: CLI and library built exclusively on native Node.js APIs. No third-party supply-chain risk, minimal cold-start overhead.

NOTE:A focused, shippable tool that solves a real LLM-context problem with a craftsman's restraint: do one thing well, with no dependencies you don't need.
